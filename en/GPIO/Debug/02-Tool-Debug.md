## 2. SWD Probe

### What is SWD and why it's the most important protocol

SWD (Serial Wire Debug) is the standard debug protocol for all ARM Cortex-M microcontrollers. It uses only 2 wires plus ground:

- **SWCLK** (Serial Wire Clock) -- Clock generated by the debugger
- **SWDIO** (Serial Wire Data I/O) -- Bidirectional data line

Compared to JTAG (which requires 4-5 wires), SWD is simpler, takes fewer pins, and offers the same functionality for Cortex-M. For this reason, the vast majority of IoT devices with ARM MCUs have exposed SWD headers on the PCB.

### SWD protocol architecture

The SWD protocol is based on a packet model:

```
Host (Flipper) --> Target (MCU)
   |                    |
   |--- SWCLK (clock) -->|
   |<-- SWDIO (data) --->|
   |                    |
   [Debug Port (DP)]
        |
   [Access Port (AP)]
        |
   [Memory Bus / Core Registers]
```

**Debug Port (DP)**
- First level of access
- Contains registers IDCODE, CTRL/STAT, SELECT, RDBUFF
- The IDCODE identifies the chip (essential to know what you're debugging)

**Access Port (AP)**
- Second level, selected via the DP's SELECT register
- MEM-AP: access to the MCU's AHB bus (memory, peripherals, flash)
- JTAG-AP: for downstream JTAG chains (rare)

**Fundamental operations via SWD:**

| Operation | Description | Use in pentesting |
|---|---|---|
| Read IDCODE | Identifies the target chip | First thing to do to know what you have in front of you |
| Halt CPU | Stops execution | Necessary to read flash without interference |
| Resume CPU | Resumes execution | After you're done inspecting |
| Read Memory | Reads memory addresses | Flash dump, RAM, peripheral registers |
| Write Memory | Writes to memory | Firmware patching, configuration modification |
| Set Breakpoint | Breakpoint | Live firmware debugging |
| Flash Program | Programs the internal flash | Upload modified firmware |

### Operational procedure with the Flipper Zero

**Physical connection:**

```
Flipper Zero          Target MCU
-----------          ----------
Pin 2 (SWCLK)  -->  SWCLK
Pin 3 (SWDIO)  -->  SWDIO
Pin 8 (GND)    -->  GND
```

> IMPORTANT: The target must be powered from its own source. The Flipper can provide 3.3V from pin 9, but only for low-consumption targets (< 100mA). For MCUs with external peripherals, use the device's original power supply.

**Step 1 -- Connection and identification:**

1. On the Flipper: GPIO -> Debug -> SWD Probe
2. The Flipper attempts the SWD connection
3. If the target responds, it reads the IDCODE
4. The IDCODE identifies the manufacturer and chip model

Common IDCODE table:

```
IDCODE          | Chip
----------------|---------------------------
0x1BA01477      | STM32F1xx (Cortex-M3)
0x2BA01477      | STM32F4xx (Cortex-M4)
0x6BA02477      | STM32H7xx (Cortex-M7)
0x0BC11477      | nRF52832 (Nordic)
0x0BC12477      | nRF52840 (Nordic)
0x01002927      | RP2040 (Raspberry Pi)
```

**Step 2 -- Halt and inspection:**

Once connected, you can:
- Halt the CPU (stop execution)
- Read core registers (R0-R15, PSR, MSP, PSP)
- Inspect memory at any address

**Step 3 -- Firmware dump:**

Dumping the internal flash is the most important operation. Every MCU has flash mapped at specific addresses:

```
Chip          | Flash Start  | Typical Size
--------------|-------------|-------------------
STM32F103     | 0x08000000  | 64-128 KB
STM32F411     | 0x08000000  | 512 KB
nRF52832      | 0x00000000  | 512 KB
nRF52840      | 0x00000000  | 1 MB
RP2040        | 0x10000000  | 2-16 MB (external flash)
```

From the Flipper, you can read the entire flash range and save it to the SD card as a binary file. This file can then be analyzed with:
- `binwalk` to extract filesystems and components
- `strings` to search for credentials and URLs
- `Ghidra` for complete disassembly
- `radare2` for rapid analysis

### Readout Protection (RDP) -- The pentester's enemy

Readout Protection is the mechanism that prevents flash reading via debug. Each manufacturer implements it differently:

**STM32 -- RDP (Read-out Protection)**

| Level | Description | Bypassable? |
|-------|-------------|-------------|
| RDP 0 | No protection | Yes -- free read |
| RDP 1 | Flash protected from external read, debug possible | Partially -- glitch attacks exist |
| RDP 2 | Debug completely disabled, irreversible | No -- the chip is "bricked" for debug |

The field reality: the majority of consumer IoT devices have RDP 0 (no protection). Manufacturers don't activate readout protection to simplify production and firmware updates. This means that in most cases, the SWD dump works on the first attempt.

> Personal note: out of approximately 40 IoT devices I've analyzed in real assessments, only 3 had RDP activated at level 1 and none at level 2. And of those 3 with RDP 1, two still had the external SPI flash readable without protection. The takeaway is clear: always try SWD first, because the odds are in your favor.

**Nordic nRF52 -- APPROTECT**

| State | Description |
|-------|-------------|
| Disabled | Free access via SWD |
| Enabled | Blocks access to flash and RAM via debug |

APPROTECT is enabled by writing a specific value to the UICR (User Information Configuration Register) register. To disable it requires a full chip erase, which deletes all the firmware. Only useful if you want to reprogram the chip, not for extracting the original firmware.

Note: on older versions of the nRF52 (pre-2020), there was a vulnerability in the APPROTECT mechanism that allowed bypassing it via a glitch on the reset pin during boot. This vulnerability has been corrected in subsequent silicon revisions.

**RP2040 -- Secure Boot**

The RP2040 itself has no native readout protection on the external flash. The flash is external SPI and can be read directly. In the RP2350 revisions, Secure Boot with OTP (One-Time Programmable) fuses was introduced.

### Firmware dump -- Detailed procedure for STM32

This is the step-by-step procedure for dumping the firmware of an STM32F103 (one of the most common chips in cheap IoT devices):

1. **Identify the SWD pads on the PCB**
   - Look for 4-pin headers labeled SWD, DBG, J-Link
   - In the absence of labels, look for 1.27mm pads in groups of 4
   - Use the multimeter to identify GND (continuity with ground plane)
   - SWCLK and SWDIO are typically pulled up to 3.3V (resistance toward VCC)

2. **Connection**
   - Solder temporary wires or use pogo pins / test clips
   - Connect SWCLK, SWDIO, GND to the Flipper
   - Power the target from its original source

3. **SWD connection**
   - Start SWD Probe on the Flipper
   - Verify that the IDCODE is read correctly
   - If it doesn't respond: check wiring, verify the target is powered

4. **Flash read**
   - Select memory read
   - Start address: 0x08000000
   - Size: depends on the chip (check the datasheet)
   - The Flipper saves the dump to the SD card

5. **Dump verification**
   - The file should start with the reset vector (first 4 bytes = initial stack pointer address)
   - A valid STM32 dump has the first 4 bytes pointing to the end of RAM (e.g., 0x20005000)
   - The second 4 bytes point to the reset handler in flash (e.g., 0x080001xx)
   - If the dump is all 0x00 or all 0xFF, something went wrong

### Firmware dump -- Procedure for nRF52

Nordic nRF52 chips are ubiquitous in BLE devices: fitness trackers, sensors, beacons, smart locks.

1. **nRF52 SWD pinout**
   - SWDIO and SWCLK are always available
   - Optional reset pin (useful if the chip is in deep sleep)

2. **nRF52832 memory map:**
   ```
   0x00000000 - 0x0007FFFF  Flash (512 KB)
   0x10001000 - 0x100010FF  UICR (configuration)
   0x20000000 - 0x2000FFFF  RAM (64 KB)
   ```

3. **Complete dump:**
   - Flash: 512 KB from 0x00000000
   - UICR: 256 bytes from 0x10001000 (contains BLE configuration, keys, parameters)

4. **Typical nRF52 flash structure:**
   ```
   0x00000000 - 0x00000FFF  MBR (Master Boot Record)
   0x00001000 - 0x00025FFF  SoftDevice (Nordic BLE stack)
   0x00026000 - 0x0007BFFF  Application firmware
   0x0007C000 - 0x0007FFFF  Bootloader
   ```

5. **Post-dump analysis:**
   - The SoftDevice is proprietary Nordic firmware (not very interesting)
   - The application firmware contains the device's logic
   - The bootloader may contain DFU (Device Firmware Update) keys
   - Search the UICR for BLE keys and configuration parameters

> Personal note: BLE devices based on the nRF52 are the most fun to analyze. The application firmware is often small (50-100 KB), which makes reverse engineering with Ghidra much more manageable compared to 16 MB Linux firmware. Plus, the Nordic SDKs leave many debug symbols in the firmware, which enormously facilitates code comprehension.

## 3. DAP Link

### CMSIS-DAP -- The industrial standard for ARM debugging

DAP Link (Debug Access Port Link) implements the CMSIS-DAP (Cortex Microcontroller Software Interface Standard - Debug Access Port) standard. It is a protocol standardized by ARM that defines how a hardware debugger communicates with debug software on the PC.

The Flipper Zero, when operating in DAP Link mode, presents itself to the PC as a USB CMSIS-DAP compatible device. This means you can use it with any tool that supports this standard:

- **OpenOCD** (Open On-Chip Debugger)
- **pyOCD** (Python On-Chip Debugger)
- **Keil uVision**
- **PlatformIO / VSCode**
- **IAR Embedded Workbench**

### Difference between SWD Probe and DAP Link

| Aspect | SWD Probe | DAP Link |
|--------|-----------|----------|
| Interface | Standalone (Flipper display) | USB to PC |
| Control | Directly from the Flipper | From software on the PC |
| Functionality | Dump, basic flash | Full debug, step-through |
| Breakpoints | Limited | Full (hardware + software) |
| Memory watch | Manual read | Real-time continuous |
| Suited for | Field assessment | In-depth lab analysis |

In practice: the SWD Probe is for quick field work. DAP Link is for when you return to the lab and want to do serious debugging with all the tools.

### Setup with OpenOCD

OpenOCD is the most widely used open-source tool for embedded debugging. Configuration for using the Flipper as a probe:

**Installation:**
```bash
# Debian/Ubuntu/Kali
sudo apt install openocd

# macOS
brew install openocd

# Arch Linux
sudo pacman -S openocd
```

**Configuration file for Flipper Zero DAP Link:**

Create a file `flipper-dap.cfg`:
```
# CMSIS-DAP interface (Flipper Zero)
adapter driver cmsis-dap

# SWD speed (in kHz) -- start low, increase if stable
adapter speed 4000

# SWD transport
transport select swd
```

**Connection to an STM32F103 target:**
```bash
openocd -f flipper-dap.cfg -f target/stm32f1x.cfg
```

Expected output:
```
Open On-Chip Debugger 0.12.0
Info : CMSIS-DAP: SWD supported
Info : CMSIS-DAP: FW Version = Flipper Zero DAP v1
Info : SWCLK/TCK = 1 SWDIO/TMS = 1
Info : cmsis-dap: SWD IDCODE = 0x1ba01477
Info : stm32f1x.cpu: Cortex-M3 r1p1 processor detected
Info : stm32f1x.cpu: target has 6 breakpoints, 4 watchpoints
```

**Essential OpenOCD commands for pentesting:**

```bash
# Telnet connection to OpenOCD (port 4444 by default)
telnet localhost 4444

# Halt the CPU
> halt

# Dump flash to file
> flash read_image firmware.bin 0x08000000 0x20000

# Dump RAM
> dump_image ram.bin 0x20000000 0x5000

# Read single register
> reg r0
> reg pc
> reg sp

# Read memory (32 bit)
> mdw 0x08000000 16

# Write memory
> mww 0x20000000 0xDEADBEEF

# Read readout protection
> stm32f1x options_read 0

# Reset the target
> reset halt
> reset run

# Flash new firmware
> program nuovo_firmware.bin 0x08000000 verify reset
```

### Setup with pyOCD

pyOCD is a Python-native alternative to OpenOCD, simpler to use for quick operations:

```bash
# Installation
pip install pyocd

# List connected probes
pyocd list

# Connection and interactive shell
pyocd commander --target stm32f103rc --probe cmsis-dap

# Commands in the pyOCD shell
>>> halt
>>> read32 0x08000000
>>> read8 0x08000000 256
>>> savefile firmware.bin 0x08000000 0x20000
>>> reg
>>> resume
```

### Live debug -- Step-through with GDB

Step-by-step debugging is fundamental when you want to understand firmware behavior in real time:

**Starting GDB server via OpenOCD:**
```bash
# OpenOCD exposes a GDB server on port 3333
openocd -f flipper-dap.cfg -f target/stm32f1x.cfg
```

**Connection with GDB:**
```bash
# Use arm-none-eabi-gdb or gdb-multiarch
arm-none-eabi-gdb firmware.elf

# Inside GDB
(gdb) target remote localhost:3333
(gdb) monitor reset halt
(gdb) break main
(gdb) continue
(gdb) step
(gdb) next
(gdb) info registers
(gdb) x/16xw 0x08000000
(gdb) print variable_name
```

If you don't have the ELF file with symbols (typical case in pentesting -- you're analyzing extracted firmware), you can still use GDB for assembly-level debugging:

```bash
gdb-multiarch

(gdb) target remote localhost:3333
(gdb) set architecture arm
(gdb) monitor reset halt
(gdb) x/20i $pc          # Disassemble from program counter
(gdb) si                  # Step instruction (single instruction)
(gdb) ni                  # Next instruction (skip calls)
(gdb) break *0x08001234   # Breakpoint at specific address
(gdb) watch *0x20000100   # Watchpoint on RAM address
```

### Integration with PlatformIO / VSCode

For those who prefer a graphical IDE:

1. Install PlatformIO in VSCode
2. In the `platformio.ini` file:
   ```ini
   [env:debug]
   platform = ststm32
   board = genericSTM32F103RC
   debug_tool = cmsis-dap
   upload_protocol = cmsis-dap
   debug_speed = 4000
   ```
3. Connect the Flipper in DAP Link mode
4. F5 to start debugging with graphical breakpoints, memory view, register view

> Personal note: the Flipper Zero DAP Link + VSCode + PlatformIO combo is the setup I use most often in the lab. It's quick to configure, graphical debugging makes it much easier to follow the firmware flow, and the real-time memory view is priceless for understanding what the code does. For the field, I use the standalone SWD Probe. For serious analysis, DAP Link always.
